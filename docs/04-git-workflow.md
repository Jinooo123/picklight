# Git 协作规范

## 1. 仓库与分支

- `main` 只保存可运行或可评审版本。远程仓库创建后开启分支保护，禁止直接推送，至少 1 位同伴评审后合并。
- 每项任务使用独立分支：`feat/issue-编号-简述`、`fix/issue-编号-简述`、`docs/简述`。分支从最新 `main` 创建。
- 一项 PR 只处理一个明确目标。跨端功能可拆成关联的前端与后端 PR，用同一个 Issue 串起来。
- 合并方式建议 squash merge；合并后删除远程功能分支。发布演示版本使用 `v0.1-demo` 等标签。

## 2. 提交与评审

提交标题使用 `feat: ...`、`fix: ...`、`docs: ...`、`test: ...`、`chore: ...`，说明变更结果。PR 描述包含对应需求 ID、改动、验证步骤和界面截图（有 UI 时）。评审重点是权限、异常路径、接口兼容、测试及是否误提交密钥或大型媒体文件。

普通流程：更新 `main`，创建分支，提交小步改动，推送分支，发起 PR，评审修复，合并。遇到冲突先与涉及文件的负责人沟通，合并时重新运行相关测试。

## 3. 接口与数据变更

- API 字段、状态码、数据库结构变更必须同时更新 `docs/02-architecture.md` 或后续独立 API 文档，并在 PR 标明影响的小程序/后台模块。
- 数据库结构使用迁移脚本，禁止让组员手工修改共享库后不提交脚本。
- 密码、令牌、微信密钥和本机配置放入被忽略的本地配置。仓库只提交 `.env.example` 或配置示例。
- 示例媒体使用可公开展示且体积小的文件；上传目录与数据库运行数据不提交。

## 4. 远程仓库接入

本地仓库初始化后，欧阳文锦自行创建 GitHub 或 Gitee 空仓库，并在本目录运行：

```powershell

git push -u origin main
```

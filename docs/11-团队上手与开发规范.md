# 团队上手与开发规范

给七个人看的操作手册。照着做就能拉代码、写代码、提 PR。遇到报错先看第 8 节。

## 1. 先装环境

| 端 | 需要装 | 验证命令 |
| --- | --- | --- |
| 通用 | Git、Python 3.10+ | `git --version`、`python --version` |
| 小程序 | 微信开发者工具、HBuilderX 或 Node 20 | 能打开项目并预览 |
| 管理端 | Node 20 + npm | `node -v`、`npm -v` |
| 服务端 | JDK 17、Maven 3.9、MySQL 8 | `java -version`、`mvn -v`、`mysql --version` |

装完 `git --version` 能出版本号即可，不用追求最新版。

## 2. 把仓库拉下来（只做一次）

**先配 SSH，不要用 HTTPS。** 校园网把 `github.com` 解析到一个连不通的地址，HTTPS 会卡在 21 秒后报 `Failed to connect`。SSH 走 443 端口不受影响。

```bash
# 1) 生成密钥，一路回车（可以不设密码）
ssh-keygen -t ed25519 -C "你的邮箱"

# 2) 查看公钥内容
cat ~/.ssh/id_ed25519.pub

# 3) 打开 https://github.com/settings/keys → New SSH key → 粘贴这一整行
#    公钥只能加到本人账号，别人代加不了
```

在 `C:\Users\<你的用户名>\.ssh\config`（没有就新建）写入：

```text
Host github.com
  HostName ssh.github.com
  Port 443
  User git
```

```bash
ssh -T git@github.com          # 出现 Hi <用户名>! 就成功
git clone git@github.com:Jinooo123/picklight.git
cd picklight
sh scripts/setup-dev.sh        # 启用提交钩子，必做
```

Windows 用 `powershell -ExecutionPolicy Bypass -File scripts/setup-dev.ps1`。

**公钥和私钥是什么**：`ssh-keygen` 会生成一对文件，`id_ed25519` 是私钥（钥匙，只能留在自己电脑上，谁要都别给），`id_ed25519.pub` 是公钥（锁，可以随便发）。把锁交给 GitHub，以后你用钥匙开门，GitHub 认得出是你，就不用每次输密码。私钥泄露等于别人能冒充你提交，公钥泄露没有任何风险。

**需要加协作者**：仓库是公开的，谁都能下载，但**只有协作者能上传**。欧阳文锦要在 Settings → Collaborators 里把其余 6 人加进来，权限选 Write；不加的话，即使公钥配好了，推送也会报 `ERROR: Permission to Jinooo123/picklight.git denied`。

**每人用自己的 GitHub 账号**，公钥加到自己账号的 Settings → SSH and GPG keys 里。不要图省事把别人的公钥加到你的账号下——那样他的提交会记在你名下，而且他能推你所有的仓库。

## 3. 每天怎么开工

```bash
git switch main && git pull              # 1. 拿最新代码
git switch -c feat/T-201-media-picker    # 2. 从 main 开分支，名字带任务编号
# ...写代码...
git add -A && git commit -m "feat(T-201): 媒体选择与预览"   # 3. 小步提交
git push -u origin feat/T-201-media-picker                  # 4. 推分支
```

然后在 GitHub 上点 **Compare & pull request**，标题格式与提交一致，描述里写 `Closes #12`（12 换成你的 Issue 号），勾完自查清单，找一个人评审。

**红线**：`main` 不能直推，推了会被拒；不要 force push；不要提交 `.env`、密钥和上传的媒体文件。

## 4. 我的任务在哪

打开仓库 **Issues** 页，按里程碑筛选（M1 是这周），标题形如 `[T-201] 媒体选择与预览`。每个 Issue 里写了负责人、预估工时、依赖、验收标准和开工命令。

只做自己名下的 Issue。要做别人的，先在群里说一声，改 Issue 负责人。

## 5. 代码怎么写

**顺序不能反**：契约 → 库表 → 骨架 → 业务 → 联调。第 1 周先把这四件事做完，第 2 周才开始堆功能，否则前后端对不上接口，返工比重写还慢。

**每个模块的写法**（以“发布动态”为例）：

1. 先看 `docs/08-api-contract.md` 里 `POST /posts` 的请求体与响应，照着写，不要自己发挥字段名；
2. 服务端：`Controller` 只做参数校验与鉴权，业务逻辑放 `Service`，SQL 放 `Mapper`；错误统一 `throw new BizException(Code.XXX)`，由全局异常处理转成 `{code, message}`；
3. 小程序/管理端：所有请求走封装好的 `request`，不要在每个页面里写 `wx.request`；
4. 页面必须有四态：加载中、空数据、失败可重试、正常；这四态是验收标准里明确要求的；
5. 提交前自测：正常路径 1 条、异常路径 2 条（比如超长、越权），跑通了再提 PR。

**不要做的事**：

- 不要改别人模块的文件。要改接口就在 Issue 里 @ 对方，或提 PR 让对方评审。
- 不要在代码里写死 `localhost:8080`，走配置文件。
- 不要把 `console.log` / `System.out.println` 提交上去。
- 不要一次 PR 改 20 个文件。一项任务一个 PR，评审才看得动。

**命名**：Java 类 `PostService`、方法 `createPost`；Vue 组件 `PostCard.vue`；接口路径全小写中划线 `/api/v1/admin/posts`；数据库表和字段用下划线 `post_tags`。

## 6. 提交信息与 PR

```text
feat(T-201): 媒体选择与预览
fix(T-305): 连点导致重复评分
docs: 补第 1 周会议记录
test(T-509): 补动态检索边界用例
chore: 升级 Element Plus
```

格式不对会被钩子直接拦下并提示正确写法。PR 描述写清楚：关联 Issue、改了什么、怎么验证、截图（有界面时）。

**评审看四件事**：权限有没有漏（越权能不能改别人数据）、异常路径有没有处理、接口字段有没有变动、有没有误提交密钥或大文件。

## 8. 常见报错

| 报错 | 原因与处理 |
| --- | --- |
| `Failed to connect to github.com port 443` | 没用 SSH。按第 2 节配 `~/.ssh/config`，把 origin 换成 `git@github.com:...` |
| `Permission denied (publickey)` | 公钥没加到 GitHub，或加错了账号。`ssh -T git@github.com` 复测 |
| `ERROR: Permission to ... denied` | 你不是协作者。让欧阳文锦在 Settings → Collaborators 里加你，权限 Write |
| `Key is already in use` | 这把公钥已经加在别的账号上。一个公钥只能加一个账号，重新生成一对 |
| `Key is invalid` | 粘错了内容，粘成了私钥或只粘了一部分。重新 `cat ~/.ssh/id_ed25519.pub` 整行复制 |
| `protected branch hook declined` | 在往 `main` 推。改成推自己的分支再开 PR |
| `Updates were rejected`（non-fast-forward） | 远程有你没有的提交。`git pull --rebase` 后重推 |
| 冲突（CONFLICT） | 别乱删标记。找冲突文件的作者一起看，改完 `git add` 再 `git rebase --continue` |
| 钩子没生效 | `git config core.hooksPath` 应为 `.githooks`，不是就重跑 `scripts/setup-dev.sh` |
| `gh: TLS handshake timeout` | 校园网问题，与本项目无关。批量操作改用 `scripts/bootstrap_github_api.py` |

## 10. 公共文件与冲突

七个人改一个仓库，最容易出事的不是业务代码，是**大家都想改的那几个文件**。约定好归属，冲突能少八成。

### 10.1 公共文件只由一人改

| 文件 | 谁统一改 | 别人怎么做 |
| --- | --- | --- |
| `apps/miniprogram/pages.json`、`manifest.json` | 欧阳文锦 | 需要加页面/改 tabBar，在群里说，别自己动 |
| `apps/admin/package.json`、`vite.config.js`、`src/router/index.js` | 黄佳佳 | 需要装新依赖或加路由，报给她 |
| `services/api/pom.xml`、`application.yml` | 梁文博 | 需要加依赖，先说用途，由他加 |
| `docs/06-task-breakdown.md`、`docs/tasks.csv` | 欧阳文锦 | 任务有变，改 `scripts/gen_task_docs.py` 后重新生成 |
| `.github/`、`.githooks/` | 欧阳文锦 | 觉得规则不合理，提意见，不要直接改 |
| `README.md` | 欧阳文锦 | 内容明显过期就在群里说 |

其余文件各改各的：你自己的页面、你自己的 Controller、你自己的 Service，谁也不碰谁的。

### 10.2 冲突了怎么办

看到 `CONFLICT (content): Merge conflict in xxx` 不要慌，五步解决：

```bash
git switch main && git pull          # 1. 先拿最新
git switch 你的分支                   # 2. 回自己分支
git rebase main                      # 3. 变基，这里会报冲突文件
# 4. 打开冲突文件，删掉这三行标记，保留正确内容：
#    <<<<<<< HEAD
#    =======
#    >>>>>>> xxxx
git add 冲突文件 && git rebase --continue
git push --force-with-lease          # 5. 变基后必须强推（加 --force-with-lease，别用 -f）
```

冲突文件是两个人都在改的，**改之前先问对方那段是他的还是你的**，不要凭感觉删。

### 10.3 减少冲突的三条习惯

1. 每天开工第一件事 `git pull`，不要连着三天不拉。
2. 分支别超过三天，做完就提 PR 合并，不要攒着。
3. 一个分支只改一件事。改页面的分支里不要顺手改 `pom.xml`。

# 依赖关系与风险

版本：V1（2026-11-20）。解释「谁卡住会拖累谁」，以及每个人按什么顺序做。任务定义以 [`06-task-breakdown.md`](06-task-breakdown.md) 为准，这里是依赖视角的汇总。

## 1. 核心结论

> **后端是上游，前端是下游。上游慢，下游全等；下游慢，只影响自己。**

七个人的活儿不是各干各的，而是一条链。最上游的是**梁文博的契约与库表**，他晚一天，下周前端三个人就晚一天开工。所以第一周的实际策略是：**先保梁文博这条链，其他人先做不依赖契约的活。**

## 5. 应对「上游慢」的降级办法

1. **契约定稿前**：前端不要等契约，先用「假数据」把页面画出来，字段名后面批量替换。
2. **接口没做好时**：前端用 mock（本地写死的假接口）先跑通交互，等真接口好了只换请求地址。
3. **卡住超过半天**：群里报任务号，别自己扛到周五。上游的人更要主动说进度，别让下游白白等。
4. **梁文博如果被卡**（比如考试）：T-003 契约可以拆——账号组先出，动态组跟上，不必一次写全。
